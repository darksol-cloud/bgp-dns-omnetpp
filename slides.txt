Problem Statement
2
In DTN, nodes are identified by EIDs. Applications must know which EIDs are reachable and how to forward bundles to them.

A DTN Node Must Know:
1) Which EIDs currently exist(e.g., new services, applications, or agents joining/ leaving)
2) Which next-hop neighbor can forward toward each EID(“To reach EID X, send bundles to neighbor Y over CLA Z.”)
3) What convergence layer parameters to use(CLA type, address, port, security keys, QoS attributes)
4) When reachability becomes invalid(EIDs disappear, CLAs go down, applications terminate)

Problem
Challenge
3
❶ No continuous connectivityNodes may be offline for minutes–hours–days.
❷ No broadcast or multicast “flooding”Not acceptable in DTN-over-IP or SSI-scale systems.
❸ Multi-hop, transitive reachabilityA gateway may reach EIDs beyond the immediate neighbor.
❹ Heterogeneous convergence layers at each hop.TCPCL, UDPCL, MTCP, QUIC, etc.

Extend the Internet’s BGP to carry DTN-specific NLRIs (Network Layer Reachability Information) for EIDs.
Each NLRI carriesEID prefix, originator, next-hop CLA endpoint, optional metadata.
BGP UPDATE messages propagate NLRIs following normal BGP rules.
• Reachability propagates across multiple AS hops 
• Changes announced incrementally with UPDATE/WITHDRAW
Every BGP-enabled DTN router maintains a DTN-FIB mapping

Resolve EID → CLA endpoint mappings on demand using DNS, without maintaining a distributed control-plane
Hierarchical namespace: EIDs are mapped to DNS zones (e.g., 978879.ipn.arpa)
Resolution via standard DNS queries: PTR, SRV/SVCB, A/AAAA
A BP Agent can resolve any reachable EID using DNS lookups
• On-demand resolution, Hierarchical authority
• Decoupled from routing: DNS gives the BP endpoint, not paths

BGP vs. DNS Approaches
A Quantitative Comparison
First running simulation setup using INET’s Omnet++ Library
Feeling for the moment: INET feels like overkill for the analysis(too complicated to configure, with multiple parameters down to the Link layer that makes evaluation very complicated)
BGP relies on persistent TCP/QUIC sessions between neighbors. When links flap, gateways reboot, or intermittent connectivity appears, these sessions repeatedly reset, triggering slow reconvergence or long hold-times. UPDATE/WITHDRAW propagation pauses while sessions re-establish. BGP degrades under frequent outages or DTN-style disruption.

DNS is fundamentally stateless on the client side. Queries are retried over multiple paths/resolvers and benefit from: Caching, Redundant authoritative servers, Store-and-forward UDP behavior.
